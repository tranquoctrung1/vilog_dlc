# VilogLDC WinForms Conventions

## Why this exists

This is a small, single-developer legacy WinForms app with no build automation and no tests. Conventions here exist to keep changes consistent with the existing code rather than to enforce a "correct" architecture the project never adopted.

## Project layout

- `SerialCom/VilogLDC.vbproj` — the only project (`OutputType: WinExe`, `TargetFrameworkVersion: v4.8`, `AssemblyName/RootNamespace: VilogLDC`).
- `SerialCom/Form1.vb` + `Form1.Designer.vb` — the entire application logic lives in `Form1.vb`; `Form1.Designer.vb` is generated by the WinForms designer and should only be touched by adding/renaming controls through the designer, not by hand-editing control logic there.
- `SerialCom/popupMonitorScreen.vb` — a secondary form, currently minimal (near-empty), tied to `SerialPort3`'s monitor/log link.
- `SerialCom/My Project/` — standard VB.NET project scaffolding (`AssemblyInfo.vb`, `Settings.designer.vb`, `Resources.designer.vb`) — rarely needs edits.
- `Note.txt` — informal changelog, one line per notable change, mixed English/Vietnamese, no strict format. Append new entries in the same terse style when you make a user-visible fix (see `vb-winforms-developer` agent).

## Control naming

Controls are named by the WinForms designer's default numbering (`Button1`..`Button15`, `ComboBox1`..`ComboBox5`, `TextBox1`..`TextBox12`, `RichTextBox1`..`RichTextBox4`) — there is no semantic renaming convention. When referencing a control in code you're adding, look up what it does by reading its handler/nearby code (e.g. `ComboBox5` = flowmeter type selector, `ComboBox3`/`ComboBox4` = reporting/logging interval selectors) rather than guessing from the number.

## Threading

Two background execution paths exist:
- `SerialPort.DataReceived` events (fire on a thread-pool thread).
- `sendingThread` running `SendLoop` (a `Thread`, `IsBackground = True`).

Any control access from either must be marshaled via `Invoke`/`InvokeRequired`. This is covered in depth by the `vilog-serial-protocol` skill for the serial-specific handshake; the same rule applies to any other background work you add.

## Build & verify

- There is no CI and no automated test suite. `msbuild`/`devenv` are not necessarily on this machine's PATH — check with `where msbuild` / `where devenv` before assuming you can build from the command line; if neither is available, say so explicitly rather than claiming a build was verified.
- If a build tool is available, build with the `.vbproj` (not the missing `.sln` reference — note there's a `VilogLDC.sln` at the repo root that should be checked for validity if using it).
- Manual verification against real hardware (serial ports, actual Dragino/flowmeter devices) is the only real test for protocol-layer changes — flag this limitation to the user rather than claiming a fix is confirmed working.

## Licensing gate

`Form1_Load` checks the machine's MAC address (`nics(1).GetPhysicalAddress`) against a hardcoded allow-list (`Licence` array) — currently the enforcement (`Me.Close()`/disabling buttons) is commented out, so the check is inert. Don't silently re-enable or silently remove this enforcement — if a task touches this code, flag the change explicitly to the user since it affects who can run the app.
